# SpecHub UI 方案

> **定位一句话**：Web 端不是「文档阅读器」，是「契约可信度的操作台」——三扇门里的 Web 入口，人用 Web 管理同一份 git 化 OpenAPI spec。
>
> **角色**：评审草稿 v0.1　**日期**：2026-11-14　**状态**：待评审（关联：[产品方案](SpecHub-产品方案.md) §5.3 / [开发计划](SpecHub-开发计划.md) H 组与 P2 I 组）

---

## 0. 摘要

产品方案的差异化在 **git 真源 + 版本 + 可信**，Web UI 的视觉语言必须反过来对齐：第一语言是 **diff / 版本 / 归属仓**，编辑器是正文，Draft/Release 与仓库同步状态是全局可见的可信表达。YApi 是「文档编辑工具」，SpecHub 不能做成另一个表单堆叠；Apifox 的接口列表工作台值得对标，但要砍掉平台级能力。

**三条硬事实决定 UI 口味**：
1. **真源在文件里，Web 只是入口之一** —— 编辑一律面对「这文件还要过 git」的现实，保存即 commit + push；
2. **`specJson` 已是干净的 JSON** —— 详情页数据源现成，不需要重新建模；
3. **接口 / AI 文档是两个独立管理域**（§5.7 / §6.2）—— 但**不能做成两个产品**，要同一个壳。

**一句话记住本方案**：三区壳 + 双入口；接口列表是核心导航单元；详情页三段式（契约 / 交互 / 溯源）；编辑器正文是文件；双域同壳不同节奏、链接串起。

## 1. 定位：可信度操作台，不是文档阅读器

### 1.1 与竞品的视觉语言对照

| 产品 | 视觉语言 | SpecHub 的取舍 |
|---|---|---|
| YApi | 表单 + 编辑器堆叠（文档编辑工具） | 不学。git 真源能力在这里无表达 |
| Apifox | 接口列表即工作台、功能密度极大 | 学列表工作台，砍订阅流 / 环境变量等平台能力 |
| Swagger UI | 只读渲染 | 唯一可借 —— 契约区渲染的成熟模式 |
| Notion / 语雀 | 阅读型排版 | 文档侧（Doc 域）的对标 |

### 1.2 三个约束条件

前文「三条硬事实」，落到每条对 UI 的直接要求：

| 硬事实 | UI 直接要求 |
|---|---|
| 真源在文件里 | 编辑页必须诚实表达「在编辑真源文件」；保存 = diff → commit → push，不是局域网内的 DB 写入 |
| specJson 已干净 | 详情契约区的数据源直接来自 `GET /apis/{id}` 的 `specJson`，解析渲染即可，不建中间模型 |
| 双域分离 | 同一个壳，域切换用分段控件；Docs 有 relatedApis[] 链接位，接口侧有对应「相关文档」位 |

## 2. 信息架构：三区壳 + 双入口

```
┌────────────────────────────────────────────────────────────┐
│ 顶栏  品牌 · 项目空间切换 · draft/release 视图开关 · 搜索 · 用户  │
├──────────────────────────────┬─────────────────────────────┤
│ 侧栏                          │  主区                        │
│   接口（主入口）                │  （按侧栏选择的域渲染）          │
│   ├─ 仓库列表（带 sync 状态）   │   接口列表 / 接口详情 / 编辑     │
│   └─ AI 文档（辅入口）          │   或  目录树 / 文档阅读 / 渲染    │
│      └─ 文档目录树             │                             │
│ 底层：变更轨迹（跨域抽屉）       │                             │
└──────────────────────────────┴─────────────────────────────┘
```

- **接口侧** = 工具型布局（紧凑表格、过滤器、方法色标签）—— 接口列表即工作台，但对标 Apifox 时只留信息密度，去掉平台级能力。
- **文档侧** = 阅读型布局（目录树 + 渲染 + TOC 联动）—— 对标语雀，克制在「只读 + 轻评论」（评论 P2 I5）。
- **不做**：全局级联 404 美化页、向导式 onboarding（工程工具不是 SaaS consumer）。首次进入直接是「仓库列表 + 空状态引导卡」，一步引导注册第一个仓。

### 2.1 双入口的同一性

两个域共用顶栏 + 外壳，仅主区与侧栏下半渲染不同。**产品心智是「同一仓库的知识」**，不是两个独立产品。

## 3. 组件级关键决策

### 决策 1 · 接口列表 = 核心导航单元（不是普通表格）

列表每一行回答消费者三个问题：**调什么**（method + path）、**干嘛的**（summary）、**从哪来**（归属仓 / tag）。

- 行 = `METHOD 彩色徽标 + path(等宽) | summary | tag | 归属仓 | 同步状态`。
- **方法色是唯一彩色来源**（GET 绿 / POST 蓝 / PUT 橙 / DELETE 红 / PATCH 紫），其余一律中性 —— 接口工具的本体，App 级配色为它让位。
- 左分组 = 仓库（§7.3 多仓汇入，UI 展示「哪个仓提供哪个接口」）。
- top pin：**draft / release 切换开关全局可见**（§6.4 决策 5）—— 用顶栏控件，不藏二级页。

### 决策 2 · 详情页 = 三段式：契约 / 交互 / 溯源

```
┌─ 头：METHOD + path + summary + 归属仓 + 版本 badge ─────────────┐
├───────────────────────────────────────────────────────────────┤
│  ① 契约          ② 交互           ③ 溯源                          │
│  Parameters      Try it out      归属仓 / commit / 变更记录       │
│  RequestBody     (P2 I1)         Version / specHash            │
│  Responses       Mock 预览        diff 入口 (git 白给)           │
│  Schema 树        (P2 I2)                                       │
├───────────────────────────────────────────────────────────────┤
```

- **① 契约区**是本体：Schema 树用**可折叠递归树**、ref 可点击跳转，不要表单化平铺（OpenAPI 嵌套结构表单化必死）。渲染模式借鉴 Swagger UI 但做减——去掉其花哨分组。
- **② 交互区**标 P2 灰，H 组不落地。
- **③ 溯源区**是「可信」的直接表达：展示 specHash、归属仓、版本序号、变更 diff 入口（D4）。
- 溯源区字段现状已全在（`specHash` 在 Version、`specJson` 里含原始数据），只差 UI 与两个对外拆字段，见 §6。

### 决策 3 · 编辑器正文是文件，不是表单

H5 的 Monaco 双栏方向对，语义明确为：**编辑 `specs/xxx/openapi.yaml` 文件**。

- 走 H4 写回链路（`PUT /repos/{id}/spec`）， **保存动作的真实含义 = commit + push**，UI 诚实表达：保存前给 diff 预览 + 「提交信息」确认步骤（默认 `chore(spechub): update {path}`，对齐 SpecWriter 线上提交文案）。
- 编辑页顶部 = 面包屑 `specs/petstore/openapi.yaml` —— 让用户永远知道真源在 git，这是**产品叙事的界面化**。
- **双栏建议改为「YAML 编辑器 | 实时渲染预览」**（渲染引擎复用详情页契约区），不做 YAML↔JSON 互转（互转失真，是老 spec 工具的幻觉）。

### 决策 4 · 双域分离的 UI 表达 = 同壳不同节奏，链接串起

- 域切换 = 侧栏分段控件（接口 / AI 文档），不拆独立 URL 空间。
- 链接关联：文档下方「关联接口」区（§6.3 `Doc.relatedApis[]` 的 UI 位）；接口详情页有「相关文档」反向位。
- Doc 域 v1 克制：目录树 + Markdown 渲染 + 全文检索（P2 K2 FTS5）。评论留 P2 I5。

## 4. 视觉语言与主题

三个词：**克制、紧凑、信任**。开发者工具，不是消费产品。

| 维度 | 建议 | 理由 |
|---|---|---|
| 信息密度 | 对标 Apifox / GitHub 紧凑表格，不做卡片瀑布流 | 接口列表的信息密度是生产力，卡片反生产力 |
| 主色 | 单一品牌色仅做强调（深靛蓝族，如 `#3B5BDB`）+ 方法色 set | 方法色承担辨识，品牌色只负责选中 / 主行动 / 品牌 |
| 字体 | 中文正文系统栈；**path / specJson / 哈希用等宽**（JetBrains Mono 或系统 mono） | 契约工具的可信度来自等宽精确性 |
| 深浅 | 双主题，默认跟随系统 | 工程团队两派都有 |
| 空状态 / 错误 | 空状态给「注册仓库」下一步；`sync_status=error` 行级标红 + 可看 lastError | 可信叙事，错误必须可见可查 |
| 状态语言 | `ok / error / syncing` 用小圆点 + 文本，不用红绿灯隐喻 | 红 = 错误、黄 = 同步中，绿隐喻是消费产品语言 |

### 4.1 警示：不做「炫」

不加图表 / 动效 / 渐变点缀。「这是可信的工程基础设施」的观感来自**克制**：等宽、网格、方法色、一像素边框，而不是任何一帧动效。

## 5. 跨端一致性（差异化护城河的界面回响）

三扇门读写同一份 spec 是产品壁垒，UI 用一致性把它表达出来：

- **导航 / 命名一致**：Web 的项目、接口路径、tag 与 MCP 工具参数（`search_api` 的 q/method）、CLI 命令语义一一对应 —— 同一个 query 在 Web 搜索框与 MCP 工具里给出同一批结果。
- **可见即可被 AI 用**：Web 显示的每个接口，MCP 拿到的都是同一份 specJson；UI 要表达「你在看的就是 AI 也会看的那份文件」。
- **H6 登录不是装饰**：是「写操作皆审」（§6.4 决策 3）的前置 —— 登录 + 角色决定编辑入口可见性。

## 6. H 组落地范围与后端配合

### 6.1 范围控制（对齐开发计划 H1–H6）

| 做（H 组） | 延后（P2 I/K） | 明确不做 |
|---|---|---|
| 三区壳 + 双入口（H1） | Try it out / Mock 预览（I1/I3） | 卡片瀑布流 / 炫动效 |
| 项目 / 仓库 / 接口列表（读，H2） | RBAC 真实落地（I4；H6 只做登录占位） | Guide 式 onboarding |
| 接口详情三段式（含溯源区，H3） | Doc 域全文检索（K2） | YAML↔JSON 互转双栏 |
| Monaco 编辑 + commit 确认（H4/H5） | 评论（I5） | 环境变量 / 订阅流等平台能力 |

### 6.2 需后端配合的小扩展

1. **溯源区对外拆字段**：`GET /apis/{id}` 返回值补 `specHash` / repo 元数据（url / branch / syncStatus）。数据在库里有，只差序列化层拆出来。`ApiRecord` 加对应字段或聚合时带上 `RepoRecord`。
2. **`GET /apis` 支持 tag 过滤**：接口列表按 tag 筛分组的后端支持（RepoController 的 `GET /repos/{id}/apis` 已有 method/tag/q，ApiQueryController 的全局版没有）。
3. **`Doc.relatedApis[]` 反向位**：接口详情「相关文档」的查询接口（P2 K 落一起加，H 组可不做）。

### 6.3 H 组脚手架技术栈（对齐 §7.4 依赖方向）

- React + Vite + TS，Monaco editor；走 REST JSON，永不 import JVM 产物。
- 组件库建议 **shadcn/ui（Radix + Tailwind）**：方法色 / 紧凑表格 / 双主题都可控，避免引入重 UI 框架。
- 路由建议用 React Router；状态管理先不引（列表 + 详情 + 编辑器三个页面，props 足够，避免 Redux 类重镇）。

## 7. 开放问题

- **O1（已向用户提出）· 保存是否强制 diff 确认**：编辑保存时强制走「diff 预览 + 提交信息」步骤，最契合「可信」叙事但多一步操作；偏 YApi 的旧用户（§9 R1 收编诉求）会嫌重。待拍板：强制确认 / 可配置（默认开）/ 仅对「新建」强制。
- **O2 · draft / release 开关在 I6 落地前**：UI 先做开关占位，I6 前语义 = release 即当前快照、开关仅切换无 draft 数据时的空态提示。是否接受此中间态？
- **O3 · 登录形态**：H6 用 admin token 简单登录占位（对齐 E8 `--seed-admin`），还是直接引 OIDC 骨架？后者工程量大，倾向前者占位、P2 I4 一起换。
