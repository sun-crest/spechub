# SpecHub 产品方案

> **定位一句话**：以 git 化契约文件为真源的接口文档平台——Claude Code 读写、人用 Web 管理、IDE 插件注入，三方永远围绕同一份 OpenAPI spec。
>
> **角色**：评审草稿 v0.1　**日期**：2026-11-10　**状态**：待团队评审

---

## 0. 摘要

接口文档的痛不是"不好看"，而是"不可信"。YApi/Apifox 把文档存在数据库里，维护靠人肉，AI 工具（Claude Code）进不去；mock 与文档脱节；文档永远是滞后的。

SpecHub 换个思路：**文档即源码**。AI 产出的研发知识——接口契约、接手项目分析、需求分析——都以 OpenAPI 3.1 / Markdown 的文件形式保存在 git 仓库里，版本化、可 diff、可回滚；在此基础上建立三扇门——**Claude Code（MCP/CLI）**、**Web 管理界面**、**IDE 插件**——三方读写同一份文件，一改全改。

**三件事记住 SpecHub**：

| # | 核心差异 | 一句话 |
|---|---|---|
| 1 | **AI 优先** | 接口、接手分析、需求说明都是文件，Claude Code 用最自然的方式直接读写，不需要"爬进入口" |
| 2 | **契约真源** | OpenAPI 单一模型，mock / 调试 / 导出 / 契约测试从契约长出来 |
| 3 | **IDE 注入** | 从路由与注解一键导入，编辑器里 hover 即见定义 |

**当前决策**：名字定为 **SpecHub**（中文副名「契书」），命名查重已完成（见附录 A），主流域名被占但 `.io` 可注册，品牌面无撞车。产品重心 = **API 接口管理优先**；AI 接手分析、需求分析等认知文档作为**辅助层**，与接口文档**分开管理**（独立管理域，见 §5.7 / §6.2）。部署默认内置 Gitea 文档仓托管（可切换外部 git 托管，见 §7.3）。代码尚未开始，P0 待开工。

## 1. 背景与问题

### 1.1 现状痛点

- **文档维护靠人**：接口改了，YApi/Apifox 里没人同步，前端拿着过期的文档联调。
- **AI 进不去**：2026 年的开发工作流里 Claude Code 已是主力，但它只能读代码，读不了数据库型平台里的文档——"看着文档改代码，改完码再手改文档"。
- **mock 与文档脱节**：mock 数据跟 spec 不绑定，联调时"假数据对不上真字段"。
- **契约无版本**：变更没有 diff、没有审批、没有审计，出事找不到源头。
- **跨团队联调无主**：接口分布在各服务的代码仓里，谁生产、谁消费、变更谁受影响——没人说得清。
- **AI 分析结果无处沉淀**：接手项目用 Claude 摸代码、做需求分析，结果散在聊天记录里，下次接手又要重新分析一遍。

### 1.2 机会窗口

- AI coding（Claude Code）成为日常，2026 年 MCP（Model Context Protocol）是标准接入协议——**"AI 能读能写的契约层"** 是一个真实的新入口。
- AI 对代码库的认知（接手、重构、resume）是重复产出的高频资产，缺一个 git 化落点与"AI 能读的目录"。
- 谁先提供这层能力，谁就从"工具"变成"工作流本身"。

---

## 2. 产品定位与差异化

- **对谁说**：中小型研发团队（前后端 5–50 人），已经在用 AI coding 工具。
- **解决什么**：AI 产出的研发知识（接口契约、接手分析、需求）的"可信度"与"AI 可达性"。
- **和谁竞争**：YApi（开源但停滞）、Apifox/ApiPost（商业化，AI 不是一等公民）、SwaggerHub/Stoplight（重、贵、面向大型企业）；通用文档 Confluence/Notion/语雀（无 AI 一等公民、无契约能力）。
- **差异化壁垒**：git 化的契约文件使得 **AI 读写、ide 注入、契约测试** 成为同一套能力的三个出口，这不是"加个 AI 按钮"能抄走的。

---

## 3. 命名与品牌

- **英文名**：SpecHub —— spec(规格/契约) + Hub(枢纽)：**"研发规格的单一 git 真源"**——像 GitHub 之于代码，SpecHub 之于研发规格：接口契约 + AI 分析 + 需求说明同仓。
- **中文名**：**契书** —— 契约之书，AI 与人共同读写的一本书。作为全量文档层的副品牌，兜住接手分析等 Markdown"非契约"内容。
- **分层叙事**：主品牌 SpecHub 锁"契约/规格"（Api），文档层用「契书」/ SpecHub Docs（Doc 类）——一个锁规格、一个兜全量文档；对外一句话："研发文档单一真源，接口与分析同仓"。
- **关键结论**：可用。品牌检索无撞车产品；`spechub.io` 可注册（注意 `.io` 有 2025 主权移交后的退役传闻，需 `spechub.cn` / `getspechub.com` 兜底）；GitHub org 名 `spechub` 已被无关学术项目占用，组织名改 `spechubhq`；npm 名被占，发布统一走 `@spechub/*` scope。

## 4. 目标用户与核心场景

| 角色 | 核心诉求 | 典型场景 |
|---|---|---|
| 新接手项目者 | 快速摸清现状、留痕复用 | 接手老项目，用 Claude 分析代码生成认知文档入仓，团队日后查看不再重复分析 |
| 后端开发 | 文档随代码同步、不添负担 | 改完接口，Claude 顺手把 spec 更新提交，diff 完 push |
| 前端/客户端开发 | 拿到可信契约、能即刻 mock 联调 | 前端不知接口细节，让 Claude 按 spec 直接生成联调用例 |
| 测试/QA | 有契约做校验、变更可追溯 | 契约测试断言响应符合 spec，接口变更留痕 |
| 技术负责人 | 文档是资产而非负担 | 评审文档变更、审计访问、对外发布文档门户 |

## 5. 功能全景

```
┌─────────────────────────────────────────────────────────┐
│                    接入层（三扇门）                       │
│   Claude Code        Web UI（人）        IDE 插件         │
│  (MCP + CLI)         类 YApi             一键导入          │
└──────────────────────────┬──────────────────────────────┘
              ┌────────────▼────────────┐
              │       存储内核           │
              │   git 化文件真源 + 索引    │
              │  OpenAPI 3.1 单一模型    │
              └────────────┬────────────┘
   ┌───────────────────────┼───────────────────────┐
   ▼                       ▼                       ▼
  Mock 服务              导出/发布               工程化/协作
 读 spec 生成            MD/Word/PDF/HTML        Webhook/契约测试/评审
```

### 5.1 存储内核（P0，决定成败的地基）

「文件 + git」是**内部引擎，不是用户门槛**。内核按**两端模型**工作：

- **生产端**：spec 以文件形式存在于各后端团队**自己的代码仓**（见 §6.2），Claude 直接读写、随代码 PR 一起 review——对生产者零新增动作。
- **聚合层**：平台经 webhook/CI 将多仓 spec 汇入统一索引，归一化为 OpenAPI 3.1 单一模型，按项目逻辑隔离 + RBAC。消费者（前端/APP/QA/下游团队）**只看聚合发布视图，不碰 git**。
- **接口与文档分域（接口优先）**：`Api`（结构化契约，第一优先：mock/调试/契约测试/订阅）与 `Doc`（AI 分析等自由文档，辅助）是**两个独立管理域**：各自目录、检索、发布与权限，用链接关联而非混同管理；共享 git / 版本 / 评审基础设施。
- 唯一数据模型 `project / repo / doc / api / schema / mock / version / changelog`，三个入口写它；文件才是真源，git 白嫖 diff/回滚/审计。

### 5.2 Claude Code / AI 通道（P1，核心差异）

- **MCP Server**：注册 `search_api`、`get_api`、`list_projects`、`create_api`、`update_api`、`doc_sync_status` 等工具。默认只读，写操作需确认（权限分层）。
- **CLI 工作流**（类 git）：`spechub pull / push / status / diff / commit`，日常节奏是"改代码 → AI 更新文档 → diff → 提交"。
- **本地写、远端读**：本地代码仓的 spec 由 Claude 原生文件工具直接读写（无需 MCP）；平台聚合层经 **remote MCP(HTTP)** 访问；CLI 承担 push/pull 同步与 CI 校验。
- **AI 辅助能力**：从代码仓库自动生成/同步文档、文档与代码一致性检查、自然语言需求 → API 草案、废弃接口清扫。
- **AI 分析入库**：接手项目 / 需求分析等 AI 产出，以文件落入 `docs/` **独立域**、进索引，随 git 版本化，日后可查可审计——与接口契约分开管理。

### 5.3 Web 管理界面（P1→P2，类 YApi）

- 项目/分组空间、成员角色权限（owner/admin/editor/viewer）。
- 双栏 Markdown 编辑 + 表单式 Schema 编辑。
- **在线调试**（Try it out）、**Mock 自动生成**（按 spec + 规则引擎）。
- 变更记录 / 评论 / 版本快照 / 评审审批流。
- **变更订阅与发布快照**：消费团队订阅所依赖的接口，结构变更时收到通知；draft（仓内）→ release（对外快照）分流，消费者默认读 release，"文档又过期"从根上消失。
- **双入口界面**：接口（主入口）与 AI 文档（辅入口）分开浏览；AI 文档提供目录树 / 全文检索 / Markdown 渲染，可链接到实现接口。

### 5.4 IDE 插件（P2→P3）

- **VSCode 优先 + JetBrains**。扫描路由（Spring/Express/FastAPI/Koa/Django…）、抽取 JSDoc/Docstring 注解 → 生成 spec → 一键 push 到平台。
- 编辑器内 hover 显示接口定义、跳转文档；提交时 lint 提示"文档和代码不同步"。

### 5.5 导出与发布（P2）

- 导出 **Markdown · Word(.docx) · PDF · HTML**。
- 导出标准 **OpenAPI / Postman collection**（网关、测试工具复用）。
- 生成公网**静态文档站点**（类 ReadMe.io，可对外发布）。

### 5.6 工程化与协作（P3）

- Webhook / CI：代码 push 自动触发文档校验。
- **契约测试**：用 spec 断言接口响应，"文档是假的"当场暴露。
- git 化白给的副产物：**变更即 diff、可回滚、可审计**。

### 5.7 AI 文档层（P2，辅助层 · 与接口分开管理）

- **接口优先、文档为辅**：产品主轴始终是接口契约（mock/调试/契约测试/订阅）；AI 分析文档是辅助资产，不喧宾夺主。
- **独立管理域**：AI 分析/需求文档放在 `docs/<服务>` 独立域，与接口 `specs/<接口>` 分开管理——各自目录、检索、发布与权限，通过链接交叉引用，而非混在同一个项目里。
- 新接手项目的代码结构/功能分析、开发期的需求分析等 AI 产出以 Markdown 落仓，走同一套版本/评审/订阅——"AI 分析过就留痕"。
- **范围克制**：只收 AI 产出的研发知识（分析 / 设计 / 契约），不收会议纪要、团队 wiki——那是另两个搅局战场。

## 6. 系统架构与数据模型

### 6.1 分层架构

```
生产端代码仓 (真源/git) ──▶ 平台聚合层 (摄取/索引/发布/订阅) ──▶ 接入层 (MCP/CLI/UI/插件) + 消费端(只读)
```

### 6.2 生产端目录规范（两个独立管理域，挂在各后端团队代码仓内）

接口契约与 AI 文档**分开管理**：接口为主、文档为辅，各成一个独立管理域，用链接关联而不混同。

```
specs/<api-name>/                  # 域一：接口契约（第一优先）
  openapi.yaml                     # 机器可读的 spec 真源
  schema/
    user.yaml                      # 可拆分引用的实体 schema
  notes.md                         # 该接口的人工补充说明（SLA、注意事项）

docs/<service-name>/               # 域二：AI 分析文档（分开管理）
  handover-code-analysis.md        # 接手项目：代码结构 / 功能分析
  requirements.md                  # 开发期：需求分析
  changelog.md                     # 变更记录
```

> 对 Claude Code 的意义：文件即数据，`openapi.yaml` 与 Markdown 都可直接读写与 diff，"AI 用最自然的方式工作"。两域边界清晰：改接口进 `specs/`，产认知进 `docs/`。

### 6.3 数据实体

| 实体 | 说明 | 关键字段 |
|---|---|---|
| Project | 项目空间 | name, members, roles |
| Repo | 后端代码仓（spec 来源） | url, branch, webhook, syncStatus |
| Doc | 自由文档（AI 分析/需求） | title, markdown, tags, sourceRepo, relatedApis[] |
| Api | 接口 = method + path + tag + owner | method, path, request, response[], auth, ownerRepo |
| Schema | 实体定义 | ref, fields[], nullable, enum |
| MockRule | mock 生成规则 | pattern, value, script |
| Version | 发布快照（draft / release） | specHash, changelog, stage |
| Subscription | 消费订阅 | apiRef, team, notifyOn |
| ChangeLog | 变更记录 | actor, diff, reason, review |

### 6.4 关键设计决策

1. **文件即真源**：一切入口最终写生产端代码仓，git 处理并发与历史；平台聚合层只建索引、不改持有。
2. **OpenAPI 单一模型、摄入兼容多版本**：内部只存在一个模型（OpenAPI 3.1），mock / 调试 / 契约测试 / 订阅全部只认它。版本兼容只放在**摄入这唯一的边界**上做：外部 2.0 / 3.0 / 3.1 一律在摄取时升级映射进内部 3.1，原始文件原样保留在真源、绝不回写重写；导出主推 3.1，仅对旧工具链提供 3.0 降级，2.0 不做（有损且无需求）。详见 §6.5。
3. **写操作皆审**：AI 写的文档默认进"待确认"，人评审后合入。
4. **接口先有主**：每个接口声明归属仓（owner），跨团队变更 = 变更请求 → owner 审批，联调不打脸。
5. **双层版本**：draft 与 release 分流，消费者默认读 release 快照；配合订阅通知替代"文档过期"。
6. **接口优先、两域分离**：产品主轴是接口契约（Api）；AI 分析等文档（Doc）是辅助层，使用独立目录与发布域，与契约链接关联而不混同管理。Doc 走文档能力（渲染 / 检索 / 评论），Api 走契约能力（mock / 调试 / 契约测试）；共享 git、版本、评审基础设施。
7. **索引可重建、写入单口**：SQLite 只是真源的可重建投影（索引），一切业务写最终落 git 文件；索引不接受直接业务写，可随时从 git 全量重建。SQLite 损坏 / 丢失 / 迁移都不构成数据事故，只为它留"可重建 = 到 git 的全量重扫管线"这一条运维纪律。

### 6.5 OpenAPI 多版本兼容（摄入边界策略）

- **摄入**：真实世界 spec 是 2.0 / 3.0 / 3.1 混杂（框架导出、存量文件、Postman/Swagger 导入）。摄取层用 `swagger-parser` 三版本自动探测解析，统一升级映射到内部 OpenAPI 3.1 模型；**原始文件原样保留在 `gitsource`，绝不回写重写**——转换只在内存/索引层一次性完成，避免"转换→再存→再转"的信息磨损。
- **转换留痕**：归一化时输出一份**升级变更日志**（`nullable: true` → `type: [..., null]`、2.0 `definitions` → `components/schemas` 等），标注"自动转换 / 需人工复核"，摄入状态走现有"写操作皆审"评审流——让"转换做了什么"可审计，落在可信度叙事上。
- **失真源头监控**（最易丢语义的三点）：可空写法（2.0/3.0 `nullable` → 3.1 `type: [..., null]`）、数值边界（`exclusiveMinimum/Maximum` 由布尔变数字）、示例与 `$defs`。自动升级约 90% 正确，10% 需人工复核——由升级日志与"自动转换 / 待确认"状态兜住。
- **导出**：标准导出输出 3.1；对旧工具链（老网关导入、旧测试框架要求 3.0）提供**只降能力**的 3.0 导出开关；2.0 导出不做（有损降级、无生态需求）。
- **远期 OAS 4.x**：转换器集中在内核一个模块，届时只改映射、模型层 API 不变——与索引层 / 托管层同一套"可替换单点"策略；对手写 2.0 的老仓库，引导先自行升级（或 AI 辅助升级，成为卖点）再入平台。

## 7. 技术选型

> 后端基准语言改为 **Java（团队 Java 主力）**；版本基准 = **Java 25（最新 LTS）+ Spring Boot 4 当前 GA 线**，随官方 GA/LTS 路线锁定小版本；前端 React 不受影响、通过 REST JSON 解耦；MCP/CLI 组件**单列评估**。

| 层 | 选型 | 理由 |
|---|---|---|
| 后端 | **Java 25（最新 LTS）· Spring Boot 4（当前 GA，Framework 7）** | Spring Boot 4 一等支持 Java 25（保留 17 基线），LTS 支持至 2033；构建时锁定当前 GA 小版本 |
| 文档存储 | **文件系统(git) 真源 + SQLite(sqlite-jdbc) 索引** | 两层分工：文件=真相（AI 直接读写、diff/回滚/评审），SQLite=可重建投影（查询/检索/发布快照/订阅）；git 操作统一走镜像内嵌的**系统 git CLI 子进程**（debug 直观、diff/merge 与团队本地行为一致；JGit 仅在批量化高频读取需要时二选一并封装为同一接口，不作主力） |
| Claude Code 接入 | **remote MCP(HTTP) 优先 + CLI；stdio 仅单机/调试** | 本地代码仓 spec 由 Claude 原生文件工具直接读写（零 MCP）；聚合层经 remote MCP(HTTP) 访问，CLI 兼 push/pull 同步与 CI 校验。官方 Java SDK，CLI 用 picocli + GraalVM native-image 打包 |
| MCP/CLI 单列 | ⚠️ **可回退 TS/Go** | Java MCP SDK 相对年轻（P1 核心体验）。若开发速度与社区资料不足，**只降级 MCP/CLI 这个组件**，不影响后端主体 |
| Web UI | **React + Vite + Monaco 双栏** | 前后端语言解耦、走 REST JSON，不随后端切换 |
| Mock | Spring Boot/WebFlux 读 spec 生成 + 规则引擎 | 高并发能力强，未来无需像 Node 那样"局部换 Go" |
| 导出 | md 模板 / docx(pandoc) / pdf(子进程) / html 静态生成 | 语言无关，免受 POI/Aspose 授权费用 |
| IDE 插件 | **JetBrains 用 Kotlin 复用后端解析器；VSCode 走 TS** | 解析器单份，JetBrains 插件直调后端库，白捡复用红利 |

**该方案与语言无关的硬骨架不变**：文件+git 真源、OpenAPI 3.1 单一模型、两端模型（生产写 / 消费读）、draft/release 双层版本。

### 7.1 部署：Docker Compose 一键拉起

- **形态**：自托管最小部署面 = 单个 `docker-compose.yml`，`docker compose up -d --build` 一键拉起；后端（Java 25）持 fatjar，镜像内嵌 git CLI 以操作真源仓库。
- **服务**：`gitea`（**默认内置的文档仓托管**，本地卷持久化；切换外部托管时可停用）、`backend`（Spring Boot：HTTP API / remote MCP / 导出子进程）、`web`（nginx 伺服静态 UI + 反代 `/api`）、`mock`（WebFlux 读 spec 生成；小团队可先合并进 backend 减部署面）。
- **数据持久化命名卷**：`gitsource`（真源文档仓）、`gitea-data`（内置 Gitea 的仓库数据）、`sqlite`（索引 DB）、`artifacts`（导出/门户产物）；容器可重建，数据不丢。
- **配置**：`SPECHUB_*` 环境变量（外部 URL、仓库路径、管理员初始化）；首次启动自动建库、初始化目录与 admin，开箱即用。
- **开发叠加**：开发阶段同一 compose 挂代码目录热更 backend，与线上拓扑一致。
- **规模演进**：compose 是自托管/开源默认形态；未来 SaaS 端再演进到 K8s，卷与数据模型保持一致。

### 7.2 索引层演进（可选：SQLite → Postgres，即 A1+B2）

- **定位**：SQLite 是四件套里**唯一的可替换件**。真源（文件+git）、git 语义、两端模型、摄取管线接口都不随索引层变化——所以这只是"换一个重建目标"，不是架构变更。
- **触发点**（满足其一再评估）：
  - 多实例部署，SQLite 单文件的跨主机并发写 / 网络卷风险成为瓶颈（索引卷**禁止**放 NFS 上）；
  - 写入并发让 SQLite 锁竞争开始拖慢摄取与查询（在"单写者"纪律下很难先到这一点）；
  - 托管/SaaS 落地，需要托管方统一管理、备份与租户隔离能力。
- **迁移路径**：数据模型与摄取管线不变，仅替换 SQL 方言与部署形态——compose 多一个 `db` 服务与卷，索引数据对 Postgres **全量重建**（源是 git 真源，天然可重建），不依赖 SQLite 数据导出；Release 快照、订阅等派生数据同样重建。
- **前置纪律**：迁移前先把"SQLite 全量可重建"当作已经交付的能力跑通（摄取器支持从 git 全量重扫、幂等续跑），迁移那一刻只是改目标库。

### 7.3 Git 托管接入（默认内置 Gitea，可切换外部托管）

- **默认形态**：compose **默认带一个 Gitea 服务**，开箱即得可写、可 push 的文档仓（数据存本地 `gitea-data` 卷）。选 Gitea：单二进制、内存要求低、docker 友好，契合"一键拉起"的轻量定位（自托管 GitLab 运维体量违背定位）。"没有既有 git 托管的团队"零门槛起步，公司内网用它做统一托管也够用。
- **切换能力**：通过**托管适配器**切换接入外部既有托管（GitHub / GitHub Enterprise、GitLab 自托管、Gitee），适配两点——`webhook 内容变更通知`（触发摄取）与 `写入回程`（push 分支 / 建 PR）；未列托管用"轮询 + git CLI"降级。切换 = 配置级动作：真源仓指向外部仓、停用 compose 里的 gitea 服务，后端逻辑不变。
- **定位不变**：平台仍是 git 的**消费者**——`clone / fetch` 镜像远程仓到 `gitsource/repos/<org>/<repo>/` 做物化与索引；Web 直改后 `push` 回真源仓分支提 PR。评审、SSO 等协作职责落在所用托管（Gitea 或外部），聚合层只做摄取 / 索引 / 发布视图。

## 9. 风险与开放问题

- **R1 · 引入门槛（核心，已拆解）**："文档上 git"的前提是把它当**内部引擎而非用户动作**。三种形态：A 独立文档仓（最重，不主推）；B spec 跟代码同仓、随 PR 提交（主推，生产者零新增动作）；C Web 直改、平台自动 commit/提 PR（兜底，收编 YApi 用户）。多仓联调下，消费者团队（前端/QA/下游）对 git 完全无感，只读平台聚合发布视图；真正的复杂度收敛在平台**聚合层**的工程里，不在用户侧。
- **R2 · AI 写文档的审批边界**：全部写操作需人确认，还是允许 AI 在指定分支内自主写？需要产品层面定策略。
- **R3 · .io 域名退役传闻**：2025 英属印度洋领地主权移交，存量 .io 域名传闻 2028–2029 后可能停止续费托管。缓解：`spechub.io`(主) + `spechub.cn`(中文/兜底) + `getspechub.com`(重定向) 三件套。
- **R4 · 生态竞争**：Postman/Apifox 也可能加 AI。差异化壁垒需要始终押在"契约测试 + AI 读写 + git 化"的组合上，而非单点功能。
- **R5 · 定位张力**：从"接口工具"扩到"AI 研发知识库"，赛道更大但对位 Confluence/Notion 更挤。守住组合拳"AI 生产 + git 真源 + 契约能力"，不做无差别 wiki。
- **O1**：开源核心 + 托管服务，还是纯商业？（决定 P3 交付形态）
- **O2**：商标注册（USPTO + 中国商标局）在上线前完成。
- **O3**：契约测试深度——先做"响应校验"还是直接上 spec-driven 双端生成。
- **O4**：AI 文档与代码版本的关联深度——按 commit 标签快照，还是"分析时点"快照即可。
